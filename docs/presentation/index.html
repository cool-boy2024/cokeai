02 · 商业模式

一件代发：不压货，赚差价

01上游货源聚合源（aibijia 公开 feed）+ 供应商店铺，分钟级同步价格与库存
→
02挑货与定价后台按类型/地区/店铺筛选，看拿货价、售价与毛利率，决定上不下架
→
03顾客下单商品页 → 两步购买 → 填邮箱/数量/验证码 → 付款
→
04人工采购运营拿采购包去上游付款，拿到卡密/账号/充值结果
→
05交付与售后订单页交付内容，质保口径以商品字段为准

收入公式

毛利 = 售价 − 拿货价 − 支付/链上成本。
没有统一加价率：订阅、Muse、接码各自按货源价与市场价定。

这套模式的硬边界

最后一步“去上游付款拿货”仍是人工。上游是带滑块验证的 SPA、没有授权 API，我们不绕过验证、不自动下单。

自动化做到“同步 + 生草稿 + 采购包”，不做到“替我们下单”03 / 16
03 · 顾客旅程

顾客从进站到拿到货，只经过 5 个页面

  • 首页：品牌环绕 + 逐词点亮的 slogan + 环形商品舞台，点进小店
  • 小店列表：按品牌筛选，现货/补货中/缺货/暂停一目了然
  • 商品详情：价格、发货时效、质保、商品介绍、重点注意事项、站内教程视频
  • 两步购买：先点“购买”，才出现支付方式；填联系邮箱、数量 1–5、人机验证
  • 订单页：进度、交付内容、售后说明；登录后在控制台也能看

设计上刻意坚持的几件事

  • 不一次性抛出支付方式，先让顾客确认商品信息
  • 发货时效、质保、退款口径全部来自商品字段，不写统一承诺
  • 教程留在站内播放，不把顾客送去外部页面
  • 重要提醒用“重点注意事项”，不藏在折叠区
小店是当前唯一面向顾客的销售入口04 / 16

06 · 商品与货源

一条货源，怎么变成一件在售商品

  • 货源：公开聚合 feed 每小时同步，记录店铺、标题、价格、库存、原链接
  • 去重：同一链接可能有多个标题/价格，用“链接 + 标题”的哈希做唯一键
  • 归类：自动识别账号 / 卡密 / 代充 / 接码，决定交付方式与表单字段
  • 建草稿：从货源生成商品草稿，文案可抄规则，但货源身份必须脱敏
  • 审核发布：运营改价、核对毛利、勾选合规，才变 active
状态是否公开含义
draft否AI/人工草稿，待审核
active是已合规确认，按库存状态展示
archived否下架，历史订单保留
in_stock是可售；另有 low_stock / out_of_stock / paused
商品页的质保、发货、退款全部读数据库字段，不写死在模板里。
货源只是进货渠道，顾客看到的永远是 CokeAI 的商品页07 / 16
07 · AI 上架流水线

点一下按钮，后台把草稿做完

01点击“AI 上架”单条或批量，最多 20 条；立刻跳转，不阻塞页面
→
02入队写任务表，通知 n8n；同一货源不会重复排队
→
03后台抓取只抓公网地址、限 512KB、逐跳校验；清洗货源身份
→
04生成草稿有 AI 配置用模型，没有就用规则提取；注意事项逐行摘录原文
→
05自动打开审核前台轮询任务状态，完成后跳到商品编辑页

为什么这样做

同步抓取会让按钮卡几秒；改成“入队 + 后台执行”后，点击约 0.4 秒跳转。

失败怎么办

失败会带原因跳回；排队超 30 分钟自动回收；生成期间仍可手动建草稿。

最后一道闸

草稿永远不公开；发布必须运营勾选合规确认，AI 不代点。

n8n 每 2 分钟兜底跑队列；webhook 用 onReceived 模式08 / 16

10 · 安全与合规

四条线，任何一条都不要越

1. 凭据只在服务器

不读取/不打印/不提交 .env、SSH 私钥、Tunnel token、后台密码、助记词、供货商与易支付凭据。不要再运行 docker compose config，它会打印生产变量。

2. 可抄规则，不露货源

店名、货源域名、外链、微信/QQ/邮箱、“货源”字样全部替换。三层兜底：生成时清洗 → 读取时兜底 → 存量 scrub 脚本。

3. 不绕过平台限制

不做 OpenAI 地区绕过、不做指纹/出口伪装；不绕上游反爬/滑块，不自动下单；不替管理员接受 Sub2API 合规确认。

4. 不说过头话

不写虚假评价、客户 Logo、增长数据；发货时效、质保、退款只用商品字段里能兑现的口径。

读到任何密钥：不转述、不落盘、不提交11 / 16
11 · 发布与回滚

分支 → PR → CI → 合并 → rsync → 重建

# 1. 开分支、提 PR；CI 必须三项全绿
build / e2e / compose-smoke

# 2. 备份当前镜像
ssh -i ~/.ssh/cokeai_deploy deploy@47.83.178.22 \
  'cd /home/deploy/cokeai && docker tag \
   $(docker compose images -q app) cokeai-app:pre-xxx'

# 3. 同步代码（保留服务器 .env）
rsync -az --delete --exclude '.env*' ... \
  ./ deploy@47.83.178.22:/home/deploy/cokeai/

# 4. 构建、重启、回源验证
docker compose build app && docker compose up -d app
curl -H "Host: cokeai.cc.cd" http://127.0.0.1:3000/api/health

回滚只有一行

docker tag cokeai-app:pre-xxx cokeai-app:local
docker compose up -d app

发布前后都要验证

  • typecheck + build；改小店逻辑再加 test:shop
  • 1440 / 390 无横向滚动；两步购买仍在
  • 生产回源 200，首页不应出现 API 销售文案
  • 商品页无外部域名与“货源”字样
main 只接受 PR；不要 force push；不要合并自己开的 PR（除非伙伴授权）12 / 16

优先级事项为什么现在做
P0审核约 50 个 AI 草稿，逐条核对价格、毛利、质保、注意事项草稿不公开，但堆着就等于没有新品

14 · 怎么接手

给伙伴和你的 AI 的开工路线

第一周

  • 读 CLAUDE.md → docs/HANDOFF.md → 本文
  • 本地起服务，把首页、小店、详情、后台走一遍
  • 用只读权限看生产：回源 curl、数据库计数、日志
  • 挑 3 个草稿做审核演练，不发布

给 AI 的硬要求

  • 先只读排查，再提方案；生产改动先说回滚
  • 结论必须有命令输出为证；失败如实贴错误
  • 不把聊天里的任何凭据写进文件或提交
  • 改 UI 前确认是不是运营要求保留的门面
遇到冲突：代码与线上实测 > HANDOFF 快照 > 历史文档；历史文档只用来理解“为什么”。
交接不是交钥匙，是把判断标准交给你15 / 16
